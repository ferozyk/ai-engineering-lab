# datasets

Everything here is synthetic. No real bank, customer, credential or specification is used. "Lab Bank" is a fictional organisation.

| Item | Location | Status |
|---|---|---|
| Corpus ("clean"): five Lab Bank OpenAPI 3.1 YAML files | `corpus/` | Version 1.0.0. |
| Corpus ("large"): the five clean files plus 48 generated specs, with a change log and an identifier catalogue | `corpus-large/` | Version 1.0.0. Generated by a script; see below. |
| Development questions (Q01 to Q15) | `evaluation/questions-dev.jsonl` | Used to build and debug the pipeline. |
| Measured questions (Q101 to Q140) | `evaluation/questions-measured.jsonl` | Frozen at version 1.0.0 (2026-11-11) after maintainer review; checksum in `manifest.json`. |
| Stress questions | `evaluation/questions-stress.jsonl` | Not written yet (manifest status `draft`). Bound to the large corpus. |
| Versions and corpus checksums | `manifest.json` | Checked by a test and by `validate-dataset`. |

The design of both is in [docs/dataset-design.md](../docs/dataset-design.md) and [docs/evaluation-methodology.md](../docs/evaluation-methodology.md).

## Versioning

- **Corpus version:** semantic version, plus a SHA-256 checksum computed over the sorted corpus files.
- **Evaluation set version:** its own version number.
- Both are recorded in the metadata of every run, so a result can always be tied to the exact data that produced it.
- The evaluation set is frozen and versioned before any measured run.

## Manifest and checksum

`manifest.json` records the corpus version, the corpus SHA-256 checksum, the version of each question set and the status of the measured set. The top-level keys describe the clean corpus. A `corpora` block repeats the clean corpus and adds the large one (version and checksum), and a `stress` block records the stress question set (version, status and, once frozen, its checksum). The checksum is computed over `name + newline + file bytes` for every corpus file in name order. Any edit to a corpus file changes it, and a test fails until the manifest is updated on purpose.

Run `uv run rag-experiment validate-dataset` to check the corpus, the chunks and both question files.

## The large corpus (`corpus-large/`)

A second, deliberately harder corpus for the stress tests of experiment 02b. It is **generated**, not hand-written: the same inputs always give the same bytes, so it can be reviewed, checked and rebuilt at any time.

| Content | Count |
|---|---|
| Documents (specs) | 53: the five clean specs, copied byte for byte, plus 48 generated specs |
| Operations | 232 |
| Chunks (with the shared chunker settings) | 2,258: 232 operation, 208 parameters, 114 request body, 1,316 response, 106 security scheme, 282 component schema |
| Largest chunk | 991 characters (limit 2,400); no chunk is split |
| Version differences recorded | 86 |
| Look-alike error codes | 265 (637 entries, one per code and version) |

What makes it harder than the clean corpus:

- **Twenty products, each in several versions.** Cards, loans, deposits, foreign exchange, disputes, beneficiaries, standing orders, direct debits, notifications, documents, identity verification, limits, rewards, merchants, webhooks, reports, savings goals, mortgages, insurance and tax forms. Each is published as separate specs `<product>-api-v1` and `-v2`; eight products (every second one by sorted name) also have `-v3`. A later version differs from the one before in two to four systematic ways: a renamed field, a larger page-size or amount maximum, a parameter that becomes required, an added or deprecated operation, a changed error meaning or status, a renamed or split scope. Everything else is identical, so a question about "version 2" has several near-duplicate chunks to choose from.
- **Look-alike identifiers.** Each product defines 12 to 14 error codes of the form `ERR-<PREFIX>-<NNN>` (for example `ERR-CRD-007`) whose descriptions differ in one detail ("the card is frozen", "the card is blocked", "the card is expired"). Field names such as `status`, `limit`, `reference` and `expiresOn` appear in many products with different meanings.
- **Duplicated catch-all content.** Every generated spec has its own `bearerAuth` scheme listing all of its product's scopes and the same shared `apiKey` scheme, as the clean specs do. This is the kind of chunk that matched many questions in architecture C.

Two machine-readable files sit next to the specs. They are not specs and are not chunked.

- `CHANGES.json`: `[{product, from_version, to_version, kind, subject, document, location, before, after}]`. `location` is a JSON Pointer into the newer spec (`document`). Question writers use it to give version questions answers that can be checked. Kinds: `field_renamed`, `page_size_max_changed`, `amount_max_changed`, `param_required`, `operation_added`, `operation_deprecated`, `error_meaning_changed`, `error_status_changed`, `scope_renamed`, `scope_split`.
- `IDENTIFIERS.json`: `[{code, product, version, document, location, status, meaning}]`, one entry per error code and version; `location` is the first response that names the code.

The generator is `rag_experiment/corpus_gen/` (vocabulary, templates, version changes, quality gates). It uses a fixed seed and no timestamps. Quality gates run on every generation and fail it if they are not met: 1,800 to 2,400 chunks, no chunk above the size limit or split, every spec parses with every `$ref` resolving, unique operation ids per document, every description ending in a full stop, the synthetic-data sentence in each `info.description`, no placeholder wording, and the five clean specs unchanged.

```bash
uv run rag-experiment generate-corpus           # write datasets/corpus-large/ and print its statistics
uv run rag-experiment generate-corpus --check   # regenerate in memory; exit 1 if a committed file differs
uv run python scripts/generate_large_corpus.py  # the same, as a script
```

After regenerating, copy the printed corpus checksum into `manifest.json` (`corpora.large.checksum`); a test and `preflight` fail until it matches.
